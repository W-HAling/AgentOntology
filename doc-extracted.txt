 01 文档概述
 1.1 文档目的
 本文档定义企业级智能体本体基座的技术架构设计方案，作为架构搭建与实施阶段的 唯一事实方案 （Single Source of Truth）。所有架构决策、技术选型、组件设计、接口规范、部署方案均以本文档为准。
 本方案解决的核心问题是：如何在一个统一平台上同时管理知识库、自主编排 AI 工作流、让工作流节点调用具备自主规划能力的智能体，并连接企业业务系统执行特定场景。

 02 架构背景与目标
 2.1 业务背景
 企业需要构建一个统一的智能体平台，该平台需要满足以下业务诉求：
 知识管理 ：管理企业内部文档、流程规范、业务数据，支持智能体按需检索
 工作流编排 ：将复杂业务场景拆解为有序的工作流，工作流的节点可以调用智能体执行
 智能体自主性 ：智能体需要具备自主规划、意图识别、任务拆解、工具调用、MCP 连接、协同 Sub-Agent 的能力
 业务系统集成 ：连接 CRM、ERP、OA 等业务系统，拉取数据并执行特定业务操作

 可组合性 ：各层独立演进，通过标准协议通信，任何一层可单独替换或升级

 03 设计原则
 3.1 协议优先（Protocol-First）
 层与层之间通过标准协议通信，而非直接函数调用。MCP 负责工具与系统接入，A2A 负责 Agent 间协作。协议优先的收益在于：任何一层的实现替换不影响其他层，且跨框架的组件可以自由组合。
 具体表现为：工作流编排层通过 MCP 协议调用工具，不直接耦合工具实现；智能体之间通过 A2A 协议通信，不依赖特定框架的多 Agent 机制。
 3.2 可组合性（Composability）
 每一层是一个独立的可替换单元。工作流编排层可以用 LangGraph，也可以在未来替换为其他图编排引擎；知识库层可以用 LlamaIndex，也可以替换为其他 RAG 框架。可组合性通过两个机制实现：
 双向 MCP ：框架既消费 MCP 工具，也暴露自身为 MCP Server，实现跨框架互调
 A2A 通信 ：Agent 之间通过结构化消息通信，不依赖共享内存或框架内部状态
 3.3 状态显式化（Explicit State）
 所有工作流状态、Agent 上下文、工具调用结果都必须显式持久化。不依赖进程内存中的隐式状态。这样设计的收益是：任何一步执行失败都可以从断点恢复，长时间运行的任务可以暂停和恢复，且状态可审计。
 具体实现方式：LangGraph 的 Checkpointer 将每个节点执行后的状态持久化到 PostgreSQL；Agent 的对话历史和工具调用记录存储在独立的会话表中；MCP 工具调用的输入输出记录在审计日志中。
 3.4 安全边界（Security Boundary）
 每一层都有明确的安全边界。工具调用必须经过权限校验，敏感操作必须触发人工审批，Agent 的权限遵循最小权限原则。安全策略在执行到达动作之前强制生效，而非依赖模型层的软约束。
 3.5 可观测性（Observability）
 Agent 的非确定性使其行为难以预测，没有全链路可观测性就无法运维。每一层都必须输出结构化的追踪数据，包括：工作流节点执行时间、Agent 推理过程、工具调用输入输出、LLM Token 消耗。可观测性从第一天就要接入，不是事后补充。

 05 工作流编排层 — LangGraph
 工作流编排层是整个基座的最顶层，负责将业务场景拆解为有序的工作流图，管理执行状态，并在关键节点调用智能体。LangGraph 是这一层的唯一选型，因为它在「图式编排 + 节点可调用 Agent + 状态持久化 + 人在回路」这四项核心能力上没有替代方案 [1] [9] 。
 5.1 状态图引擎
 LangGraph 的核心抽象是有向图（Directed Graph）。图的组成要素如下：
 要素
 类型
 说明
 State
 TypedDict
 全局状态对象，在节点间传递。使用 Python TypedDict 定义 schema，所有节点共享同一状态结构
 Node
 Callable[[State], dict]
 节点是一个 Python 函数，接收当前状态，返回状态更新（partial dict）。节点可以是：普通函数、Agent 调用、子图、或路由决策
 Edge
 str → str
 边定义节点间的固定流转关系。从节点 A 到节点 B 的直连边
 Conditional Edge
 Callable[[State], str]
 条件边通过路由函数返回下一节点名称，实现分支和循环
 Checkpointer
 BaseCheckpointSaver
 状态持久化器，在每个节点执行后自动保存状态快照

 Agent 节点的设计模式
 Agent 节点是工作流与智能体执行层的对接点。一个 Agent 节点的标准实现如下：
 from langchain.agents import create_react_agent
from langchain_mcp_adapters.client import MultiServerMCPClient
def create_agent_node(agent_config):
 """创建一个工作流节点，内部调用 Agent"""
 # 1. 初始化 MCP 客户端，连接所需的 MCP Server
 mcp_client = MultiServerMCPClient(agent_config["mcp_servers"])
 # 2. 获取工具列表（从 MCP Server 动态发现）
 tools = asyncio.run(mcp_client.get_tools())
 # 3. 创建 Agent
 agent = create_react_agent(
 model=agent_config["llm"],
 tools=tools,
 prompt=agent_config["system_prompt"]
 )
 # 4. 返回工作流节点函数
 def agent_node(state: WorkflowState) -> dict:
 result = agent.invoke({
 "messages": state["messages"],
 "plan": state.get("plan", [])
 })
 return {
 "messages": result["messages"],
 "results": [{"step": state["current_step"],
 "output": result["output"]}]
 }
 return agent_node 
 条件路由
 条件路由通过条件边实现。路由函数接收当前状态，返回下一节点名称。以下是一个意图分发路由的示例：
 def route_by_intent(state: WorkflowState) -> str:
 """根据意图识别结果路由到不同 Agent 节点"""
 intent = state.get("intent", "")
 if intent == "knowledge_query":
 return "rag_agent"
 elif intent == "data_analysis":
 return "analysis_agent"
 elif intent == "business_operation":
 return "business_agent"
 else:
 return "fallback_agent"
# 在图中添加条件边
graph.add_conditional_edges(

 "analysis_agent": "analysis_agent",
 "business_agent": "business_agent",
 "fallback_agent": "fallback_agent"
 }
)

 状态持久化是生产就绪的核心保障。LangGraph 的 Checkpointer 机制在每个节点执行后自动将状态写入持久化存储 [9] 。

from psycopg_pool import ConnectionPool
# 生产环境连接池

 max_size=20,

)

 Checkpoint 存储的数据结构包含：thread_id（会话标识）、checkpoint_id（快照 ID）、parent_id（父快照，用于回溯）、channel_values（完整状态快照）、metadata（执行元数据，含节点名称、执行时间、Token 消耗）。
 故障恢复规范 
 当工作流执行到某节点失败时，系统从最近的 Checkpoint 恢复，而非从头执行。恢复流程：
 通过 thread_id 查询最新的 checkpoint_id
 加载 channel_values 恢复状态
 从失败节点重新执行（而非从图的起始节点）
 失败节点的重试次数限制为 3 次，超过后标记 status="failed"

 Supervisor 模式实现
 Supervisor 模式通过 LangGraph 的多 Agent 图实现。Supervisor 作为路由节点，根据任务类型将执行分发到对应的专家 Agent 节点：
 from langgraph.graph import StateGraph, END
# Supervisor 决定下一步调用哪个 Agent
def supervisor_route(state):
 """根据当前状态决定委派给哪个 Agent"""
 next_agent = state.get("next_agent", "")
 if next_agent == "FINISH":
 return END
 return next_agent
# 构建多 Agent 工作流
workflow = StateGraph(WorkflowState)
workflow.add_node("supervisor", supervisor_agent)
workflow.add_node("rag_agent", rag_agent_node)
workflow.add_node("business_agent", business_agent_node)
workflow.add_node("analysis_agent", analysis_agent_node)
# Supervisor → 各 Agent → Supervisor 循环
workflow.add_conditional_edges("supervisor", supervisor_route, {
 "rag_agent": "rag_agent",
 "business_agent": "business_agent",
 "analysis_agent": "analysis_agent",
 END: END
})
for agent in ["rag_agent", "business_agent", "analysis_agent"]:
 workflow.add_edge(agent, "supervisor")
workflow.set_entry_point("supervisor")
app = workflow.compile(checkpointer=checkpointer) 
 上下文隔离
 Sub-Agent 在独立的上下文中执行，主 Agent 的上下文不会被子 Agent 的工具调用记录淹没。上下文隔离通过以下机制实现：
 每个 Sub-Agent 有独立的 messages 列表，不共享 Supervisor 的完整对话历史
 Sub-Agent 执行完成后，只向 Supervisor 返回最终结果（summary），不返回中间步骤
 DeepAgent 的 SubAgentMiddleware 实现了类似机制：通过 task 工具委派，子 Agent 的 20+ 次工具调用不会淹没主 Agent 上下文 [4]

 08 数据与知识底座层
 数据与知识底座层是整个基座的数据基础设施，由四个组件构成：LlamaIndex（知识库与 RAG）、PostgreSQL（状态持久化）、Milvus（向量检索）、Neo4j（知识图谱）、Redis（短期记忆）。这一层的设计目标是让 Agent 能够高效检索知识、持久化状态、管理记忆。

 Agentic RAG 与传统 RAG 的区别在于：Agent 自主决定检索策略、查询重写、多轮检索。Agent 不是被动地接收检索结果，而是主动判断是否需要检索、检索什么、是否需要二次检索 [13] 。

 9.1 可观测性

 # Input Guard：检测 prompt 注入
from langchain_core.guardrails import BaseGuardrail
class PromptInjectionGuard(BaseGuardrail):
 """检测用户输入中的 prompt 注入攻击"""
 INJECTION_PATTERNS = [
 "ignore previous instructions",
 "你是一个新的 AI",
 "system:",
 "忽略以上所有内容",
 "<\\/template>",
 ]
 async def avalidate(self, input_text: str) -> bool:
 text_lower = input_text.lower()
 for pattern in self.INJECTION_PATTERNS:
 if pattern.lower() in text_lower:
 return False # 拦截
 # 调用专门的分类模型进行二次检测
 is_safe = await self.classifier.predict(input_text)
 return is_safe

 9.3 成本控制
 LLM 调用是平台最大的可变成本。一个复杂工作流可能触发数十次 LLM 调用，每次调用消耗数千到数万 token。如果不做成本控制，单次工作流执行成本可能从几元飙升到几十元。成本控制从模型路由、token 预算、缓存三个层面切入。
 模型路由策略
 并非所有任务都需要最强的模型。根据任务复杂度将请求路由到不同级别的模型，可以在保持质量的前提下降低 60% 以上的推理成本。

from langchain_core.language_models import BaseChatModel
class ModelRouter:
 """根据任务类型和上下文长度路由到不同模型"""
 ROUTING_RULES = {
 "intent_classification": {
 "model": "gpt-4o-mini",
 "max_tokens": 100,
 "condition": lambda ctx: ctx["input_tokens"] < 500
 },
 "rag_summary": {
 "model": "qwen-plus",
 "max_tokens": 1000,
 "condition": lambda ctx: True
 },
 "agent_planning": {
 "model": "claude-sonnet",
 "max_tokens": 4000,
 "condition": lambda ctx: ctx["tool_count"] > 3
 },
 }
 def route(self, task_type: str, context: dict) -> BaseChatModel:
 rule = self.ROUTING_RULES.get(task_type)
 if rule and rule["condition"](context):
 return self.model_factory.create(rule["model"])
 # 默认回退到中等模型
 return self.model_factory.create("gpt-4o") 
 Token 预算管理
 每个工作流执行前分配 token 预算。当实际消耗接近预算上限时，Agent 会收到预警；超过上限时，工作流自动降级或终止。
 # Token 预算管理器
class TokenBudgetManager:
 """管理单个工作流执行的 token 预算"""
 def __init__(self, total_budget: int):
 self.total_budget = total_budget
 self.consumed = 0
 self.warning_threshold = 0.8 # 80% 预警
 self.hard_limit = 0.95 # 95% 硬限制
 def check_before_call(self, estimated_tokens: int) -> str:
 projected = self.consumed + estimated_tokens
 ratio = projected / self.total_budget
 if ratio >= self.hard_limit:
 return "BLOCK" # 阻止调用，工作流降级
 elif ratio >= self.warning_threshold:
 return "WARN" # 允许调用，但通知 Agent 节约
 else:
 return "OK"
 async def record_usage(self, actual_tokens: int):
 self.consumed += actual_tokens
 # 写入 Redis 供实时监控
 await redis.hincrby(
 f"budget:{workflow_id}", "consumed", actual_tokens
 )

 10.3 网络与安全策略
 各命名空间之间通过 NetworkPolicy 限制访问。核心原则：数据层只允许 agent-ns 和 workflow-ns 访问，obs-ns 只允许被其他命名空间 push 数据，不允许反向访问。
 # NetworkPolicy：数据层只允许 Agent 和 Workflow 访问
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
 name: data-ns-policy
 namespace: data-ns
spec:
 podSelector: {}
 policyTypes:
 - Ingress
 ingress:
 - from:
 - namespaceSelector:
 matchLabels:
 name: agent-ns
 - namespaceSelector:
 matchLabels:
 name: workflow-ns
 ports:
 - protocol: TCP
 port: 5432 # PostgreSQL
 - protocol: TCP
 port: 6379 # Redis
 - protocol: TCP
 port: 19530 # Milvus
 - protocol: TCP
 port: 7687 # Neo4j 
 10.4 GPU 资源调度
 当平台使用本地部署的开源模型（如 Qwen、Llama）进行推理时，需要 GPU 资源调度。推荐使用 NVIDIA GPU Operator + Time-Slicing 或 MIG（Multi-Instance GPU）实现 GPU 共享。

 12 实施路线图
 整个平台分为四个阶段交付，每个阶段产出可独立验证的成果。阶段之间允许重叠，但后一阶段的启动依赖前一阶段的核心能力就绪。
